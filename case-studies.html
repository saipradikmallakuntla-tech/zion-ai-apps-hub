SSE streaming inspection

Deployment scenario

An enterprise assistant streams text and proposed tool arguments through an application gateway. Before handing an incident to the platform team, inspect a sanitized saved capture to distinguish broken framing, incomplete tool JSON, and missing protocol termination.

Diagnostic procedure

  1. Open LLM Stream Inspector and select the synthetic OpenAI, Anthropic, truncated, malformed, or timestamped sample. No provider connection is opened.
  2. Inspect reconstructed text, final tool-argument JSON, findings, and the event timeline. Export the content-omitting report and review it before sharing.

Reference benchmark

The OpenAI fixture reconstructs city=Lisbon and has a terminal signal. The truncated fixture is incomplete; malformed JSON produces INVALID_JSON. Plain SSE has no invented latency. The timestamped fixture supplies first text at 125 ms and duration 400 ms.

Interpretation and limits

125/400 ms describe supplied fixture timestamps, not measured network speed. A terminal signal does not prove semantic correctness or lossless capture. Only the documented Chat Completions and Anthropic Messages adapters are supported.

Idempotent retry safety

Deployment scenario

A service commits a mutation but its response is lost. An agent, SDK, and transport each retry. Model whether one business intent becomes repeated mutations before adopting a retry policy.

Diagnostic procedure

  1. Open Agent Retry Safety Lab. Compare no key, retained stable keys, expired keys, and per-attempt keys under the same response-loss conditions.
  2. Inspect attempts, side effects, duplicates, deduplicated requests, and the timeline. Compare jitter using the same seed; it changes scheduling, not the need for server enforcement.

Reference benchmark

Reference configuration: one client; one retry at each of three layers; timeout 100 ms; service 20 ms; response-loss window 1,000,000 ms; zero backoff. Without keys: 8 attempts, 8 effects, 7 duplicates. With a stable key and 10,000 ms retention: 8 attempts, 1 effect, 7 deduplications.

Interpretation and limits

The model assumes atomic server deduplication and bounded sequential retries. TTL expiry or rotating keys can permit duplicates. It does not execute mutations, model rate limits, measure production RPS, or guarantee exactly-once delivery.

Cross-origin cookie auditing

Deployment scenario

A browser-based enterprise portal calls a separate API. A healthy API response is still inaccessible, or a session cookie is withheld. Separate CORS response access from cookie transmission eligibility.

Diagnostic procedure

  1. Open CORS & Cookie Doctor with synthetic request context, preflight/response headers, credentials mode, and cookie attributes. State the schemeful site relationship; cross-origin is not necessarily cross-site.
  2. Compare the broken/fixed credentialed CORS fixtures, cross-site Lax/None fixtures, and third-party blocking. Review findings separately from each cookie candidate. No endpoint is probed.

Reference benchmark

Credentialed wildcard origin is rejected. The explicit-origin fixture passes modeled CORS/preflight and has an eligible cookie candidate. Cross-site Lax withholds the cookie while CORS can pass. Secure SameSite=None is a candidate, but third-party policy can still block it.

Interpretation and limits

Eligibility is not proof of browser storage, authentication, authorization, or browser conformance. Public-suffix and partition-key details are not fully modeled. Confirm real behavior in approved browser DevTools; never paste live credentials.

Reproduce and record evidence

These are deterministic diagnostic reference cases, not load tests, uptime monitoring, or customer outcome statistics.

  1. Run the utilities’ built-in synthetic tests: Stream 9, Retry 10, CORS 14 (33 total). The dated release report records observed outcomes separately from these expected references.
  2. Record the engine commit, synthetic fixture/configuration, expected and observed result, UTC timestamp, runtime/browser version, and known limitations. Use the same fixture and seed for comparisons.
  3. Use synthetic or approved sanitized data. Stream exports omit reconstructed content by default; cookie reports omit values. Reports are not comprehensive secret scanners: review all exports before sharing.
  4. Validate real integrations only in an authorized environment. No live request, chaos experiment, cookie setting, production mutation, telemetry, shared backend, or model API is introduced by this suite.

Evidence checklist: owner · engine commit · fixture · expected/observed result · UTC time · environment · limitations · next action.
