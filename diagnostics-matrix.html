Failure-Mode Diagnostics Matrix & Cross-App Triage Guide

Start with the observed failure layer, not a presumed root cause. These nine failure modes and three two-way handoff recipes extend the existing case studies; they do not add engine features or production guarantees.

A bounded triage path

  1. If a browser cannot read a response or attach a cookie, separate CORS response access from cookie eligibility first. A blocked response does not prove the server did nothing.
  2. For an approved saved SSE/NDJSON capture, inspect protocol framing, terminal signals, argument JSON, and available timestamps. Do not infer missing timing or semantic correctness.
  3. If retries, response loss, or unknown mutation completion are involved, reconcile server state before replay and model stable intent identity, retention, and nested retry budgets.

Cross-app triage handoffs

Stream → retry or browser policy

Trigger: A capture is incomplete, duplicated, or unavailable to the browser.

Carry manually: Share only adapter name, event count, terminal state, structural finding codes, and timing availability; omit raw events and tool arguments.

Continue: For ambiguous completion or duplicate intent, inspect retry safety. For response access or cookie symptoms, inspect browser policy.

Stop / limits: Do not replay a mutation to repair a capture. A reconstructed answer does not establish semantic correctness.

Agent Retry Safety Lab · CORS & Cookie Doctor

Retry → stream or browser policy

Trigger: A timeout, duplicate effect, or response loss leaves the client outcome unclear.

Carry manually: Use a synthetic intent label, configured layer budgets/TTL, and modeled attempt/effect counts; never copy real keys or payloads.

Continue: Inspect stream framing for an approved saved capture, or browser policy if response access may have hidden a completed request.

Stop / limits: Reconcile actual server state separately. The simulation is not an exactly-once guarantee or a provider-contract test.

LLM Stream Inspector · CORS & Cookie Doctor

Browser policy → retry or stream

Trigger: JavaScript cannot read a response, or cookie eligibility differs from CORS access.

Carry manually: Share synthetic/redacted origin and site relationships, method, credential mode, policy findings, and whether sending/completion is known; no tokens or cookie values.

Continue: If the request may have executed, inspect retry safety before replay. Once access is understood, inspect a sanitized saved stream.

Stop / limits: No request is sent and no cookie is set by the offline tool. Confirm real behavior only in authorized DevTools; a blocked response can hide success.

LLM Stream Inspector · Agent Retry Safety Lab

Sanitized evidence and boundaries

  • Prefer built-in synthetic fixtures. Obtain approval before using any real capture or header sample.
  • Manually remove prompts, response bodies, tool arguments, Authorization/Cookie/Set-Cookie values, identifiers, and real idempotency keys. Sanitization is not automatic.
  • Record source layer, known versus unknown completion, timestamp provenance, finding codes, and the next question. Model counts must be labeled synthetic.
  • Links open independent local tools. No diagnostic input is encoded in a URL, transferred automatically, uploaded, or synchronized.

What this guide cannot establish

These are offline diagnostic aids, not live probes, browser-conformance tests, security certificates, semantic evaluators, or exactly-once guarantees. Hub documentation has full EN/ES/PT coverage; satellite interfaces remain English-only. Static/HTTPS verification is a dated observation, not a rendered accessibility audit or an SLA.
