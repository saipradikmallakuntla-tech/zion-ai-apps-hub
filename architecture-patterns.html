Architecture boundaries

Separate the production data plane from the diagnostic plane. Your authorized services own authentication, provider access, durable operation state and audit controls. These utilities analyze supplied local inputs; opening a sibling link transfers no inputs. Production is a reference context, not a claim that this static network operates your services.

Pattern: saved-stream inspection

Flow

Browser UI → authorized service or BFF → provider stream; approved saved capture → LLM Stream Inspector.

Boundary and design decision

Keep provider credentials and authorization on your service. Preserve framing and timestamp provenance while sanitizing a saved copy. Parse tool arguments as data; never execute them.

Failure and trade-off

A terminal marker is framing evidence, not semantic correctness, successful side effects or measured latency when timestamps are absent. The inspector is not a streaming proxy.

Pattern: bounded retries and idempotency

Flow

One logical intent → durable operation record → bounded attempts → reconciled outcome.

Boundary and design decision

Coordinate retry budgets across agent, SDK and transport layers. Bind a stable key to principal, operation and payload fingerprint; coordinate the ledger with the side effect and retain outcomes beyond the authorized retry horizon.

Failure and trade-off

A key alone does not make execution exactly once. Pending, expired or unknown outcomes require an authorized status read or human reconciliation before replay. This offline simulator supplies no server ledger or rate-limit enforcement.

Pattern: browser access and cookies

Flow

Browser origin → preflight/access policy → authorized API; cookie eligibility is a separate decision.

Boundary and design decision

Use an explicit trusted-origin allowlist, credentials policy and allowed methods/headers. Consider site relationship, SameSite, Secure, HttpOnly and browser third-party restrictions separately.

Failure and trade-off

CORS is not authentication or CSRF protection. An unreadable response may follow a successful mutation. The doctor reasons about supplied policy; it does not observe or configure a real browser/server.

Recipe: inspect a sanitized stream

Prerequisite

Use a built-in synthetic fixture, or an approved saved capture whose prompts, personal data, credentials and tool payloads have been manually sanitized.

Steps

  1. Open LLM Stream Inspector and select the appropriate saved-stream adapter. Do not initiate a production request.
  2. Compare a complete synthetic capture with a truncated one; inspect reconstructed text, terminal state, malformed frames and tool-argument JSON.
  3. Record only adapter, event count, structural findings and timestamp availability. If intent or completion is ambiguous, continue to the retry recipe.

Expected evidence and limits

A complete fixture and a truncated fixture should produce distinguishable structural evidence. Missing timing remains unknown; JSON validity does not authorize tool execution.

Recipe: reconcile before retrying

Prerequisite

Use a synthetic logical intent and an authorized way to reconcile server state; do not paste real idempotency keys or payloads.

Steps

  1. Open Agent Retry Safety Lab and compare stable versus rotating synthetic keys under the same loss/timeout scenario.
  2. Compare bounded layer budgets, modeled processing/timeout values, key retention and seeded jitter. Retention must cover the actual workflow horizon, not just one client timeout.
  3. Record modeled attempts/effects and known/unknown completion. In a real integration, reconcile the durable operation record before deciding whether a mutation may be retried.

Synthetic example — documentation only: demo-op-001; completion=unknown; action=reconcile

Expected evidence and limits

Stable identity can reduce modeled duplicate effects within the modeled retention window. This is not a production benchmark, actual billing count, rate-limit test or exactly-once guarantee.

Recipe: diagnose credentialed browser access

Prerequisite

Use reserved example domains and invented policy values. Determine whether the real authorized workflow is cross-origin, cross-site, or both.

Steps

  1. In CORS & Cookie Doctor, model a POST from https://app.example to https://api.example with credentials included.
  2. Check an exact allowed origin, credentials opt-in and preflight permissions for Content-Type and Idempotency-Key. A credentialed response cannot use a wildcard allowed origin.
  3. Assess cookie eligibility separately. SameSite=None requires Secure but does not override third-party restrictions; HttpOnly blocks script reads, not authorized cookie sending. Reconcile possible server completion before any replay.

Synthetic example — documentation only:

  • Access-Control-Allow-Origin: https://app.example
  • Access-Control-Allow-Credentials: true
  • Access-Control-Allow-Methods: POST
  • Access-Control-Allow-Headers: Content-Type, Idempotency-Key
  • Vary: Origin

Expected evidence and limits

Separate response access, cookie eligibility and server execution. The illustrative header set is not a deployable security policy or proof of browser behavior.

Recipe: compose the three tools

Prerequisite

Start with one synthetic intent, an approved evidence location and an explicit owner for the next action.

Steps

  1. Check browser-policy assumptions first; if a response is hidden, mark completion unknown instead of automatically retrying.
  2. Inspect an approved saved stream for framing and terminal evidence. Move only the minimal reviewed summary to the retry model.
  3. Compare retry assumptions, reconcile actual server state outside these utilities, and return the decision and evidence reference to the responsible operator.

Expected evidence and limits

Navigation is manual and carries no data. No shared backend, automatic export/import, secret scanner, monitoring or production mutation is added.

Minimal evidence contract

This invented summary is not an app import schema or API. Keep evidence in an approved internal location; replace identifiers with synthetic labels and manually review exports before sharing. Omit prompts, response bodies, tool arguments, personal data, tokens, cookie values and real keys. Never place artifacts in URL queries or fragments.

intent=demo-op-001; source=synthetic; completion=unknown; next=reconcile; contains_payload=false

Limits and safe operation

These are offline reference patterns and diagnostic aids, not security certification, legal advice, semantic-correctness proof, live browser conformance, an SLA or exactly-once assurance. A client error does not prove server failure. No automatic sanitizer is claimed.
